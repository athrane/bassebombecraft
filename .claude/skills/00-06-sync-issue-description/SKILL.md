# Skill: Sync GitHub Issue Description from a PR File

[`scripts/sync-issue.mjs`](./scripts/sync-issue.mjs) does all the mechanical work: it resolves the issue, merges the text between the `pr-sync` markers, splits overflow into comments, proposes the title and verifies the write. This skill only drives it and gets the user's click.

Run it from the repository root with Node.js 18+ and an authenticated GitHub CLI (`gh auth status`). Every command below uses this form, written `SYNC` for short:

```
SYNC = node .claude/skills/00-06-sync-issue-description/scripts/sync-issue.mjs
```

**Tip:** pass the PR file as a plain path, not `@file`, so the file is not pasted into context.

## Workflow

1. Take the PR file path from the arguments. **Do not open or read the file.**
2. Run `SYNC <file> --dry-run`.
   - Exit 2 `ambiguous-issue`: ask via `AskUserQuestion`, one option per `candidates:` issue, then re-run with `--issue N`. If it prints `candidates: (none)`, the PR file names no issue: ask for the number in plain text.
   - Exit 4 `issue-closed`: ask via `AskUserQuestion` whether to sync a closed issue; on yes, add `--allow-closed` to every later run.
   - Any other error: report the `error:` line and stop.
   - `body:` says `markers appended` and the current body is an earlier copy of the PR file (not hand-written issue text): the old copy would stay above the new one. Re-run with `--replace-unmarked` on every later run; the summary then says `unmarked body replaced`. Exit 2 `unpaired-marker` means the body holds one marker without its pair: report it and stop.
3. Show the dry-run summary through `AskUserQuestion` with the options **Apply** (recommended), **Apply, keep current title** and **Cancel**. Drop the second option when the summary says `title: unchanged`.
4. On an Apply option, run `SYNC <file> --apply --expect <plan>`, adding `--no-title` for the second option (the plan hash is the same with or without it). On exit 3 `plan-changed`, re-run step 2 and ask again.
5. Report the script's `issue:`, `part N:`/`stub N:` URL lines and `verified:`.

**Fallback:** where `AskUserQuestion` is not available, show the summary and ask for a typed yes/no.

## Project notes

- **Issue resolution:** the script reads the PR file's `## Related Issues` section: exactly one `Closes #N` wins, then exactly one `Related to #N`. Check the `issue:` line of the dry run against the file's name before clicking Apply — at least one existing file carries a `Closes #N` that does not match its filename prefix (`1455-frozen-registry-bug.md` says `Closes #145`), and the script will trust it.
- **Titles:** the title comes from the file's first `# ` heading outside a code fence. Some older requirements files have none: `1441-…` starts at `## Summary`, and `1440-…` wraps the whole file in a ` ```markdown ` fence. For those the dry run says `title: unchanged`. Files generated by `00-00-create-pr` start with the PR title as `# <type>(<scope>): <description>`, so the issue title follows the PR title.
- **Unmarked bodies:** issues created with the PR file pasted in by hand have no `pr-sync` markers. The first sync appends a marked block below the old text; use `--replace-unmarked` (step 2) when the old text is just an earlier copy of the file.
- **Cwd:** run from the repo root, so the "Full content: `<path>`" truncation notice shows a repo-relative path and `gh` resolves `{owner}/{repo}` from the git remote.

## Guard Rails

- Never run `--apply` without an explicit option click (or a typed yes in the fallback).
- Never edit labels, assignees, milestone or open/closed state; the script touches only the body, the title and its own overflow comments.
- Never hand-compose a body or call `gh issue edit` directly. If the script is wrong, fix the script.
- A dry run is read-only and always safe to run; `--apply` writes to GitHub and is visible to everyone watching the issue.
